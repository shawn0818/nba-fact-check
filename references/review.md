# 独立复核

对外发布的核查，发出去之前要由**另一个** agent 或模型独立复核。这份文件写给复核者，也写给安排复核的人。

## 为什么要分两步

复核最常见的失败是**先看到作者的结论，然后点头**：作者写了"准确"，复核者顺着证据看一遍，觉得说得通，就通过了。这样的复核什么也没复核。

所以复核分两步，顺序不能反：

1. **盲审**：只给复核者说法、核查点的问题和证据清单，**不给作者的判定和结论**。复核者自己判每个核查点。
2. **比对**：盲审交卷后，再拿出作者的判定逐点比对，并检查 display 段的措辞。

## 谁能当复核者

- 和作者**不是同一个会话**：没看过作者的检索过程和推理。最好是不同的模型或不同的 agent（例如作者是 Claude，复核用 Codex）。
- 不需要比作者更强，但必须**自己打开关键证据**，不能只读作者写的 `note`。
- **盲审期间不能翻看任何带作者结论的材料**：作者的状态块本身、作者的工作目录，以及 skill 里的 `references/cases.md` 和 `assets/examples/`——如果被复核的正好是其中收录的案例，看了就等于看了答案。安排复核时要在指令里写明。
- **复核者不能联网时**（有些 agent 的沙箱不给网络）：作者把证据的原始材料（字幕全文、报道正文或索引快照）原样放给复核者，**不附任何自己的摘录、判断或 note**，复核者在这些材料上独立判。这样的复核要在 `review.note` 里写明"离线复核"：它能查出作者读错、判错，但查不出作者漏掉的证据和反证，分量比能联网的复核轻。
- **复核者的身份以运行记录为准**：模型常常报错自己是谁（实测 Kimi 自称 GPT-5），`review.by` 写运行日志或配置里的实际模型。

## 第一步：盲审

安排复核的人用脚本生成盲审包：

```
python scripts/review_packet.py 状态块.yaml > packet.md
```

盲审包里有：原始说法和出处、每个核查点的**问题**、证据清单（链接、发布者、取证层级）、英文源的链接。**没有**：各点的判定、`finding`、`overall`、`display`、作者的 `notes`。

复核者要做的：

1. 读 SKILL.md 的铁律、判定标签和 L3 规则（判定口径要和作者一致，否则比对没有意义）。特别注意三条，第一次实测复核时 7 点里 5 点不一致，几乎都出在这里：
   - **归因还是事实**：盲审包里每个点都标了。归因点只判"那个人是否真的这样说过"，不判内容真假；事实点判这件事本身。
   - **事实点的"准确"有两种依据**：一手证据，或者两个以上互相独立、至少一个具名记者的报道一致（报道级）。不要求每件事都拿到合同原件。
   - **l3_ok 的三条**（工具进不去的平台、至少两家用原文语言逐字收录且每家都写明账号、没有反证）：满足就认，不满足就判无法证实。每家点明发帖人和平台即可，能对上具体账号更好；作者写明"账号未直接核对"时，结合媒体可靠程度和反证检索判断要不要认。帖子删除、Story 过期不算反证。
2. **逐个核查点**：打开支撑它的关键证据——至少打开每个点里取证层级最高的那条；引语类要找到原话并读到下一句；语气有歧义的引语（will 是断言还是要求、是不是玩笑）还要读完整上下文——整段讲话的主题、前后几句、场合——并在 `reason` 里写明读了哪一段，媒体标题怎么理解不能当依据；数字类自己复算。
3. 给每个点一个判定标签，写一句理由。证据不够就判"无法证实"，不要猜作者会怎么判。
4. 如果认为核查点拆错了（漏了关键的点、或者问题本身问偏了），写进 `missing_points`，并标明 `blocking`：会改变某个核心核查点或总标签的标 true（复核不通过）；外围细节标 false（复核可以通过，作者后续补核或写进 `out_of_scope`）。**这条是为了让复核能收敛**：一篇稿子里总能再找出一个没核的细节，如果每个都阻断，复核永远过不了。
5. 判断以作者的核查截止时间为准；截止之后出现的新证据可以写进 `additional_evidence` 并注明，但不用它来否定作者当时的判定。
6. 把结果写成复核结果文件（YAML）：

```yaml
reviewer: "Codex（gpt-5.6-terra）"     # 谁复核的
reviewed_at: 2026-10-19T15:00+08:00
points:
  - index: 1                           # 对应盲审包里的核查点编号，从 1 开始
    verdict: 准确
    reason: "原视频 1:23 勒布朗说 he just read off the teleprompter"
    opened: [e1]                       # 自己打开核对过的证据编号
  - index: 2
    verdict: 措辞放大
    reason: "……"
    opened: [e1, e2]
additional_evidence:                   # 自己补找的证据（可选）
  - id: r1
    url: "https://..."
    publisher: "……"
    supports: [3]                      # 支撑哪几个核查点
failed_opens:                          # 打不开的作者证据及原因（可选）
  - "e6：实时打开失败，搜索快照也拿不到"
missing_points:                        # 认为漏掉或问偏了的核查点
  - item: "……"
    blocking: true                     # 会改变某个核心核查点或总标签吗？会就是 true；外围细节写 false
notes: ""
```

## 第二步：比对

```
python scripts/review_compare.py 状态块.yaml 复核结果.yaml --write 复核后的状态块.yaml
```

脚本会逐点比对作者和复核者的判定，然后：

- **全部一致、没有阻断性漏点**：`review.status` 写 `passed`，填上复核者和时间（非阻断漏点会列出来，留给作者后续处理）。
- **任何一点不一致，或者有阻断性漏点**：`review.status` 写 `failed`，`review.note` 列出分歧；`review.points` 记下每点的双方判定。

比对通过后，复核者还要人工看一遍 display 段（脚本查不了语义）：

- `headline` 写的是真相，不是原说法；没有比证据说得更满。
- `faithful`（我们自己的译文）守住了断言强度阶梯，没有替原话补内容。
- `why` 和 `overall_scope` 与各点判定一致。
- 没有推断动机的措辞（"故意""恶意"）。
- 每个核查点引用的证据都**直接支撑**这一点：检查脚本只看证据的取证层级，挂一条无关的一手证据就能让它放行，这要靠复核者看出来。

有问题就把 `review.status` 改成 `failed` 并写明。

## 分歧怎么处理

- **不取平均，不投票。** 两边判定不一致时，回到证据本身：谁的理由有证据支撑就按谁的；都有道理就说明证据不足以下结论，往保守的方向改（通常是"无法证实"）。
- 作者修改后，要**重新复核**（可以是同一个复核者），不能自己改完就把状态改成 passed。**唯一的例外**：作者只是把有分歧的点**原样改成复核者的判定**、没有动别的，就用同一份复核结果再跑一次 `review_compare.py`，不必重新盲审——复核者已经独立判过这一点了。这条规则让复核能收敛。
- 两轮复核仍有分歧，交给人判断。
- 复核通过只说明"两个独立的判断一致"，不等于一定正确。命中 SKILL.md "交给人"那几种情形的（例如结论点名评价具体媒体），复核通过后仍要人看。

## 复核不是重新核查

复核者的任务是检验作者的结论站不站得住，不是从头再做一遍完整核查。预算参考：每个核查点打开一两条关键证据，整条核查 5 到 10 次检索以内。发现作者漏了关键证据或核查点拆错了，指出来即可，由作者补。
